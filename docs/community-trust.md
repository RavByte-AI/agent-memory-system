# Community Trust Notes

AMS should earn attention through useful technical artifacts, not broad promotion.

## Principles

- Show working artifacts before asking for attention.
- Treat benchmarks as experiments until independently reproduced.
- Invite critique on methodology and generated memory quality.
- Be specific about what AMS does and does not do.
- Prefer small technical discussions over repeated launch posts.
- Do not ask for stars, forks, or upvotes.

## Benchmark Communication

Use phrasing such as:

- "early maintainer-run benchmark"
- "reproducibility feedback welcome"
- "measured on these fixtures"
- "not yet independently reproduced"
- "raw results are available here"

Avoid certainty claims, universal performance claims, and broad superiority claims without comparable methodology.

## Contributor-Friendly Areas

- Add framework detectors.
- Add route analyzers.
- Improve graph parser coverage.
- Add benchmark fixtures.
- Add integration docs for coding agents.
- Improve generated memory validation.

## Useful Discussion Prompts

- What information should an agent always know before editing a repository?
- Should project memory live in Markdown, JSON, or both?
- How should stale generated memory be detected?
- What makes a coding-agent benchmark credible?
- How should graph blast-radius results be scored?
